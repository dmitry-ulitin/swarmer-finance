# Загрузка банковских транзакций через Enable Banking (PSD2)

## Зачем

Сейчас транзакции из банков попадают в приложение импортом выписок
(`services/import/*`, профили `lhv`, `boc`, `caixa`, `unicredit`, `alfa`). Это
трудоёмко: зайти в банк, скачать файл, выбрать счёт, загрузить. Больше всего
времени уходит на банки ЕС. У них по PSD2 есть API, и доступ к нему даёт
агрегатор Enable Banking: для подключения *собственных* счетов он бесплатен
(«restricted mode»: приложение читает только счета, которые привязал владелец
регистрации).

**Успех:** «как импорт, но без файла». На привязанном к банку счёте пользователь
нажимает «Загрузить из банка» и попадает в тот же экран предпросмотра, что и
при импорте выписки: статусы new / duplicate / possible_duplicate, подсказки
категорий, перевод на другой счёт, подтверждение через `reconcile`.

## Что проверено пробой (2026-10-23, реальная регистрация пользователя)

- JWT для API: RS256, header `{typ:"JWT", alg:"RS256", kid:<application id>}`,
  payload `{iss:"enablebanking.com", aud:"api.enablebanking.com", iat, exp}`,
  подпись приватным ключом `.pem`, который выдаёт Enable Banking. Работает.
- Новое production-приложение неактивно, пока владелец в панели Enable Banking
  не выполнит «Activate by linking accounts». До этого `/aspsps` отвечает
  403 «Application is not active». Статус появляется не сразу (около минуты).
  `GET /application` возвращает `active`.
- Все четыре банка есть (`GET /aspsps?country=`): `LHV Pank` (EE, beta),
  `Bank of Cyprus` (CY, beta), `CaixaBank` (ES), `UniCredit Bank` (RO, beta).
  У всех `psu_types` personal и `maximum_consent_validity` 180 дней.
- Поток согласия: `POST /auth` `{access:{valid_until}, aspsp:{name,country},
  state, redirect_url, psu_type:"personal"}` → `url`. Пользователь
  подтверждает в банке и возвращается на `redirect_url?state=…&code=…`.
  `POST /sessions {code}` → `session_id`, `access.valid_until`, `accounts[]`
  (`uid`, `account_id.iban`, `currency`, `name`, `product`).
- `redirect_url` должен быть одним из зарегистрированных в приложении
  Enable Banking. Работает любой https-адрес: пользователь указал страницу
  своего GitHub-репозитория, и `code` был взят из адресной строки.
- LHV отдаёт мультивалютный счёт с `currency: "XXX"`. Валюта указана в
  `transaction_amount.currency` каждой транзакции. Кредитная карта приходит
  отдельным счётом.
- `GET /accounts/{uid}/transactions?date_from=` вернул 194 транзакции за 90 дней
  одной страницей (поддержан `continuation_key`). У всех строк заполнены
  `entry_reference` (уникален), `transaction_amount {amount, currency}` (amount —
  строка без знака), `credit_debit_indicator` (DBIT/CRDT), `status` (BOOK),
  `booking_date`, `remittance_information[]`. `creditor`/`debtor` заполнены
  только у переводов (13 из 194). `merchant_category_code`, `value_date`,
  `transaction_id` пустые.
- Текст `remittance_information` совпадает с описанием из CSV-выписки LHV, а
  `booking_date` — с датой этих строк в базе. При этом `entry_reference`
  **не совпадает** с «Account servicer reference» из CSV: 7 строк LHV в базе
  импортированы из выписки с хешем, и ни одна не совпала. Ещё 1042 из 1049
  карточных строк LHV в базе вообще без хеша (перенесены из старой базы).

## Цели

1. Пользователь хранит в приложении свои ключи Enable Banking (Application ID +
   приватный ключ). Ключи **у каждого пользователя свои**: в restricted mode
   регистрация читает только счета своего владельца.
2. Пользователь подключает банк: выбирает страну и банк, подтверждает доступ в
   банке, возвращается в приложение и связывает банковские счета со своими
   счетами в приложении.
3. На связанном счёте есть действие «Загрузить из банка»: банковские транзакции
   проходят через существующий конвейер импорта и показываются на существующем
   экране предпросмотра. Сохранение идёт через существующий `reconcile`.
4. Приложение показывает, когда согласие истекает или уже истекло, и даёт
   переподключиться, не теряя связи со счетами.

## Не цели

- Фоновая синхронизация по расписанию. Пользователь выбрал ручную загрузку
  через экран предпросмотра.
- Альфа-Банк и другие банки без PSD2: для них остаётся импорт выписок.
- Платежи (PIS): только чтение счетов (AIS).
- Балансы как отдельная функция. Сверку с банковским балансом можно сделать
  позже.
- Свой коммерческий договор с Enable Banking, общая для всех ключи.
- Перенос хешей существующих строк на `entry_reference`.

## Антицели (провал, даже если «работает»)

- Дубли при переходе с выписок. Пересечение с уже импортированными или
  перенесёнными строками должно хотя бы помечаться `possible_duplicate`, и
  пользователь решает сам, как сейчас.
- Утечка ключей: приватный ключ попадает в git, в логи, в ответы API или
  хранится в базе открытым текстом. Приложение планируется размещать на
  сервере.
- Молчаливая потеря транзакций (например, PDNG-строки, которые банк позже
  проводит с другим `entry_reference`, либо обрезка по датам).
- Отдельный, второй экран предпросмотра вместо существующего.

## Ограничения

- Стек и конвенции из `CLAUDE.md`: Express + raw SQL + Zod, конверт
  `{data, error}`, миграции по порядку (следующая — `018_…`), проверки доступа в
  сервисном слое через `requireLevel`, Angular 22 standalone/OnPush/signals,
  Taiga UI v5.
- Ключи в базе шифруются мастер-ключом из новой переменной окружения (например
  `BANK_CREDENTIALS_KEY`). Без неё функция выключена и не падает. Приватный ключ
  никогда не возвращается клиенту: API отдаёт только Application ID и признак
  «ключ загружен».
- Согласие действует до 180 дней (`maximum_consent_validity` банка); запросим
  максимум, который допускает банк.
- PSD2 ограничивает запросы без участия пользователя (обычно 4 в день на счёт).
  У нас загрузку всегда начинает пользователь. Передавать ли PSU-заголовки
  (`Psu-Ip-Address`, `Psu-User-Agent`), чтобы банк считал запрос «с участием
  пользователя», — решит исполнитель по документации Enable Banking.
- Сетевые вызовы Enable Banking в тестах мокаются, как сейчас мокаются
  провайдеры блокчейнов.

## Принятые решения

**Источник данных.** Enable Banking, ключи у каждого пользователя свои
(решение пользователя). Новая регистрация должна быть активирована в панели
Enable Banking («Activate by linking accounts»). Подсказка об этом нужна в UI
ввода ключей.

**Модель подключения** (моё решение, исполнитель может уточнить схему):
- Ключи пользователя: Application ID + зашифрованный `.pem`, одна запись на
  пользователя.
- Подключение к банку (`bank_connections`): чьё оно (user_id), банк
  (`aspsp name` + `country`), `session_id`, `valid_until`, статус. Одно
  подключение = одна сессия Enable Banking = несколько банковских счетов.
- Связь счёта приложения с банковским счётом: подключение + `uid` банковского
  счёта. Валюта берётся из счёта приложения: если банковский счёт
  мультивалютный (`XXX`), строки в чужой валюте пропускаются, как
  `readStatement` пропускает их в CSV. Один банковский счёт может быть связан с
  несколькими счетами приложения (`LHV / EUR`, `LHV / USD` на один
  мультивалютный счёт LHV). Связь — новое поле или таблица; JSON `accounts.settings`
  уже используется для блокчейна, и исполнитель выберет, куда класть.
- Счёт, связанный с банком, **не** «tracked» в смысле блокчейна: его
  транзакции правятся и удаляются вручную, как импортированные из выписки.
  Счёт с блокчейн-трекингом связать с банком нельзя.

**Возврат после подтверждения в банке.** Фронтенд получает маршрут возврата
(например `/bank-callback`), который принимает `state` и `code` и завершает
подключение через backend. В UI ключей показываем адрес, который пользователь
должен прописать как redirect URL в своём приложении Enable Banking. Запасной
путь для локального запуска, когда адрес фронтенда не https: поле «вставьте
адрес из адресной строки». `state` привязан к пользователю и одноразовый.

**Загрузка.** `POST` на новый эндпоинт загрузки по счёту (рядом с
`/api/import/parse`) возвращает **тот же** `ParseResult`, что и `parseStatement`.
Для этого `parseStatement` разделяется: получение `ParsedRow[]` (из файла или из
банка) отдельно, а дальнейшее — хеши, точные и примерные дубли,
`suggestCategories`, сборка `ImportRow` — общее. Фронтенд открывает
существующий `import-review` с этим результатом. `reconcile` меняется только
в одном: он сдвигает отметку «загружено по» (см. ниже).

**Отображение полей** (моё решение):
- `date` = `booking_date`, а если его нет — `value_date`, затем
  `transaction_date`.
- `amount` = `transaction_amount.amount`; знак минус при `DBIT`.
- `description` = `remittance_information`, строки соединяются пробелом.
- `payee` = `creditor.name` для DBIT, `debtor.name` для CRDT, иначе null.
- Импортируются только `status: BOOK` (как фильтр `booked` в профиле
  UniCredit).
- Хеш = `sha256("eb|<aspsp country>|<aspsp name>|<entry_reference>")`. Если
  `entry_reference` нет — `transaction_id`. Если нет и его — контентный хеш тем
  же способом, что `computeImportHashes`. Пространство хешей отдельно от CSV:
  совпадения с выписками всё равно нет (проверено), а пересечения ловит
  эвристика «дата + сумма».

**Окно дат и отметка «загружено по»** (решение пользователя): у каждой связи
счёта с банком хранится отметка «загружено из банка по дату X».
- Первая загрузка (отметки нет) идёт с даты, которую выбирает пользователь (по
  умолчанию 90 дней назад). Следующие — с `X − 2 дня`, до сегодня. Все страницы
  забираются по `continuation_key`.
- Отметка сдвигается на `date_to` этой загрузки **только когда пользователь
  подтверждает предпросмотр**. Отмена экрана ничего не меняет, и в следующий раз
  покажется то же самое. Пропущенные при подтверждении строки (например
  `possible_duplicate` поверх старых или перенесённых строк) больше не
  предлагаются, кроме тех, что попали в перекрытие 2 дня.
- Поэтому `reconcile` получает одно изменение: необязательный признак «это
  загрузка из банка по дату X», при успехе он сдвигает отметку. Можно и
  отдельным вызовом после `reconcile` — выберет исполнитель. Подтверждение,
  в котором не выбрано ни одной строки, тоже сдвигает отметку.
- Если после подтверждения хотя бы одна строка не сохранилась, отметку не
  сдвигаем. Это защищает от молчаливой потери.

**Стабильность `entry_reference`** (проверено + моё решение): повторный
запрос через несколько часов в той же сессии вернул те же `entry_reference`.
После переподключения (новая сессия) это не проверялось. Если ID
поменяются, повтор в перекрытии поймает проверка «дата + сумма»
(`possible_duplicate`), а отметка по дате ограничивает перекрытие двумя днями.
Отдельный контентный хеш не добавляем.

**Общие счета** (моё решение): подключение принадлежит пользователю, который
его создал, и использует его ключи. Связать счёт с банком может тот, у кого на
счёте ADMIN. Загружать из банка может любой с WRITE на счёте (как сейчас
импорт выписки): данные идут в счёт, который ему и так виден. Если владелец
подключения теряет доступ к счёту, связь снимается.

**Истечение согласия.** Если `valid_until` прошло или банк ответил ошибкой
доступа, загрузка возвращает понятную ошибку («Доступ к банку истёк —
переподключите»), и счёт помечается в UI. Переподключение создаёт новую сессию
для того же банка и сохраняет связи счетов по `uid`. Если банк выдал новые
`uid`, пользователь заново выбирает соответствие. Предупреждение показываем за
7 дней до истечения.

## Оставлено исполнителю

- Точная схема таблиц и миграции, имена эндпоинтов.
- Алгоритм шифрования (подойдёт AES-256-GCM из `crypto`), формат хранения.
- Где в UI вводятся ключи (страницы профиля сейчас нет) и как выглядят
  подключение банка и выбор соответствия счетов. Нужно следовать стилю
  существующих диалогов Taiga (`account-form`, `import-upload`).
- Клиент Enable Banking (JWT, `/aspsps`, `/auth`, `/sessions`, транзакции,
  обработка ошибок) — отдельный модуль по образцу `services/chain/*`.
- Нужны ли PSU-заголовки, удалять ли сессию в Enable Banking при отключении
  (`DELETE /sessions/{id}`).

## Проверка

- Backend (Jest): шифрование туда и обратно; ключ никогда не попадает в ответы;
  отображение полей и знаков из записанного ответа LHV (данные из пробы,
  обезличенные); фильтр по валюте для `XXX`-счёта; только BOOK; пагинация;
  истёкшее согласие; права (ADMIN на связь, WRITE на загрузку); результат
  загрузки проходит `reconcile`, и повторная загрузка даёт `duplicate`;
  отметка «загружено по» сдвигается только при подтверждении, не сдвигается
  при отмене или частичном сохранении, а следующая загрузка начинается с
  `X − 2 дня`.
- Frontend (`ng test`): маршрут возврата, диалоги ключей и подключения, кнопка
  загрузки открывает `import-review`.
- Вручную на dev-базе `finance_db_nu` с реальной регистрацией пользователя
  (ключ в `backend/banks/`, в git не попадает): подключить LHV, загрузить в
  EUR-счёт LHV, где лежат строки `(..7101)…`, убедиться, что строки, уже бывшие в базе, помечены
  `possible_duplicate`, а новые после 2026-10-11 — `new`.
