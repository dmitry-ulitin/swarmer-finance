# Net Worth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A "Net worth" page with today's total, a monthly history chart and breakdowns; new account types valued by manual valuations; a per-user choice of which accounts count.

**Architecture:** Account value on a date is computed by one pure function from start balance, daily transaction flows and valuations (`services/accountValue.ts`); `/api/accounts` and the new `/api/net-worth` both use it. History is computed on request, converting month-end values at historical rates cached in `exchange_rates`. The per-user selection lives in `account_user_settings`.

**Tech Stack:** Node/Express/raw SQL/Jest; Angular 22 + Taiga UI v5 + `@taiga-ui/addon-charts`; Vitest via `ng test`.

**Spec:** `docs/superpowers/specs/2026-10-28-net-worth-design.md`

## Global Constraints

- Amounts are INTEGERs at the account's `scale` in the DB; the API takes and returns decimals (`toCents` / `toDecimal`, `services/currency.ts`).
- Envelope `{ data, error }`; errors thrown as `{ statusCode, message }`.
- "Today" is UTC (`todayUtc()` in `services/date.ts`).
- Access only through `services/access.ts` (`getAccessMap`, `requireLevel`); never filter by `transactions.user_id`.
- A rate never becomes stored transaction data; rates live only in `exchange_rates`.
- Angular: standalone, `OnPush`, `input()/output()`, `computed()`, native control flow, no `ngClass`.
- Frontend tests via `npx ng test --watch=false --include=...`, never bare vitest.
- UI copy is English, like the rest of the app ("Net worth", "Valuations", "Invested").
- New account types: `investment`, `property`, `deposit`, each with `settings` = empty strict object.

## Review Focus

1. Transfer to a valued account *after* its last valuation → value rises by the transfer the same day (no dip). Pinned in Task 3.
2. Transaction on the valuation's own date → already inside the valuation, not added again. Pinned in Task 3.
3. A user who loses access keeps no `account_user_settings` row and the account vanishes from their net worth. Pinned in Task 4.
4. Currency with no rate at all (exotic) → net worth `total` stays a number, the account is skipped and `approximate: true`, the page shows "≈". Pinned in Tasks 6 and 9.
5. Deleted account with history → in past months, not in today's total nor in `accounts[]`. Pinned in Task 6.

### Task 5: Historical exchange rates

**Files:**
- Modify: `backend/src/services/rates/frankfurter.ts`, `backend/src/services/rates/coingecko.ts`, `backend/src/services/currency.ts`, `backend/src/db/queries/exchangeRates.ts`
- Test: `backend/src/test/currencyHistory.test.ts`

**Interfaces:**
- Produces:
  - `frankfurter.fetchSeries(from, to, start, end): Promise<{ date: string; rate: number }[] | null>` uses `GET {base}/{start}..{end}?base=&symbols=`. It returns null on 404 or an unknown symbol, the same way `fetchRate` does.
  - `coingecko.fetchSeries(from, to, start, end)` uses `/coins/{id}/market_chart/range` and supports only coin→fiat, plus fiat→coin by inversion. Every other pair returns null.
    - It requests no further back than `today − 364 days`. Earlier dates are not fetched at all.
    - It keeps one price per UTC day: the last one of that day.
  - `exchangeRates.getRatesBetween(from, to, start, end): Promise<{ as_of: string; rate: number }[]>`.
  - `getRatesOn(target: string, currencies: string[], dates: string[]): Promise<Map<string, Map<string, { rate: number; approximate: boolean } | null>>>`, keyed by currency and then by date.
- Lookup rule for currency C on date D:
  - A cached row in `[D−6, D]` is exact (ECB has no weekend rates).
  - Otherwise, the nearest cached row by date is used with `approximate: true`.
  - With no row at all, the result is `null`.
  - `C === target` gives `{ rate: 1, approximate: false }`.
- Fetch rule:
  - Before the lookup, collect the dates of C with no exact row. When there are any, make one `fetchSeries` call over min..max of those dates (providers in `PROVIDERS` order) and `upsertRate` each returned day.
  - Dates that are already cached are never refetched.

- [ ] **Step 1:** Tests, with `global.fetch` mocked by URL:
  - USD→EUR on two month-ends makes exactly one Frankfurter series call and caches the rows.
  - A second `getRatesOn` call makes no fetch.
  - A Saturday date takes Friday's rate, `approximate: false`.
  - BTC→EUR at today−400d makes no CoinGecko call for that date, uses the nearest cached rate, and returns `approximate: true`.
  - An unknown currency returns null.
- [ ] **Step 2:** Run → FAIL.
- [ ] **Step 3:** Implement.
- [ ] **Step 4:** Run with `--testPathPatterns=currency` → PASS (the existing currency tests included).
- [ ] **Step 5:** Commit `feat(rates): historical rates by date`.

- Modify: `backend/src/index.ts` (`app.use('/api/net-worth', ...)`), `backend/src/test/testApp.ts` (same mount), `CLAUDE.md` (Database section: migration 019, valuations, value rule, selection, net worth endpoint; migrations "001→019")
- Test: `backend/src/test/netWorth.test.ts`

**Interfaces:**
- Consumes: `accountValueAt`, `accountStartDate`, `getAccountDailyFlows`, `listValuations` (Task 3, 2), `getNetWorthFlags`/`isInNetWorth` (Task 4), `getRatesOn` (Task 5), `getRatesTo` (today), `getAccessMap`.
- Produces: `getNetWorth(userId): Promise<NetWorthDto>`, shaped exactly as the spec's "API капитала" (decimals in `users.currency` at `currency_scale`; `accounts[].value/invested/gain` in the account's currency, `valueUser` in the user's; `gainPct` null when `invested <= 0`).
- History points: last day of every month from the month of the earliest start date or valuation among selected accounts, up to the month before the current one, then today. Each month-end uses `getRatesOn`; the today point uses `getRatesTo` and `accountValueAt(..., null)`, so it equals the account list. A point is `approximate` when any included rate is approximate or missing (missing → account skipped). `total` is never null (0 with no selected accounts; accounts without a rate are skipped and flag `approximate`).
- Deleted accounts: in history by selection, excluded from the today point, `total`, `byType`, `byCurrency` and `accounts[]`.
